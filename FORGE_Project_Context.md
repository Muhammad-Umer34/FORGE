## 1. What FORGE is

FORGE is a web-based **AI-powered multi-agent web app builder**. It is a Final Year Project (FYP) at FAST-NUCES Lahore, built by a 3-person team over two semesters (FYP-1 and FYP-2).

A non-technical user (for example a small business owner) describes a website in plain English. A team of specialised AI agents then clarifies the request, plans the site, builds it, tests it by running it, and publishes it to a shareable URL. The user never has to read or edit code.

The research question is: **does a structured multi-agent workflow make AI website generation more reliable than a simpler approach?** We will measure this in FYP-2 against a single-agent baseline, using task success, cost and speed.

## 2. Scope

- **In scope:** small websites by structure: brochure/info, catalog/grid, booking/appointment, portfolio.
- **Out of scope:** payments, complex multi-role admin systems, custom business logic, training or fine-tuning models, production-grade hosting.
- **Constraints:** no budget except about $300 in Google Gemini credits plus free tiers. Two semesters.
- **Audience:** non-technical users. They cannot fix code or errors themselves.

## 3. How the pipeline works

Each request passes through these stages:

1. **Clarification Agent:** turns a vague prompt into clear requirements (detailed in section 7).
2. **Context Retrieval Agent:** finds relevant components in the component library using vector search.
3. **Planning Agent:** produces one structured build plan (pages, components, API routes, DB schema, dependencies, execution order).
4. **Frontend, Backend and Database agents:** run **in parallel** from that plan.
5. **Integration Agent:** merges the three outputs onto a fixed project scaffold and checks their interfaces agree.
6. **Review/Test/Debug stage:** the app runs live inside a **WebContainer** (in-browser Node.js). Failures are diagnosed and routed back to the responsible generator agent, with a bounded retry limit.
7. **Live preview, then plain-English feedback, then one-click publish** (for example Netlify).

An **Orchestrator Agent** owns pipeline state, dispatches agents, validates each agent's output, and enforces the retry limit. All model calls go through an **LLM gateway** that handles provider and model config, credentials, latency and estimated cost.

**Key design choices:**
- Role-based agents with central orchestration, not free-form agent chat (predictable cost and order).
- Plan first, then generate in parallel (the plan is the shared contract).
- Reuse a tested component library, with custom-code fallback when nothing fits.
- Run generated code client-side in WebContainers, so untrusted code never runs on our servers.
- ER diagrams and the SRS document are generated by deterministic rules, with no LLM call.
- Provider-agnostic model config, so models can be swapped and compared.
- **No human escalation.** Users are non-technical, so when the retry limit is reached the request is marked **failed** with a plain-language reason, and the user can rephrase and try again.

## 5. Database design (current version)

Crow's foot ER diagram. Tables:

`USER`, `PROJECT`, `REQUEST`, `CLARIFICATION`, `REQUIREMENT`, `TEST_CASE`, `BUILD_PLAN`, `PLAN_COMPONENT`, `COMPONENT`, `AGENT_EXECUTION`, `LLM_CALL`, `MODEL_CONFIG`, `LOG_EVENT`, `GENERATED_FILE`, `TEST_RESULT`, `CORRECTION_ATTEMPT`, `GENERATED_DOCUMENT`, `PUBLICATION`. Benchmark tables are deferred for now.

Main relationships:
- `USER` owns many `PROJECT`s. A `PROJECT` receives many `REQUEST`s (an initial request or a later revision).
- A `REQUEST` has many `CLARIFICATION` rows, `REQUIREMENT` versions, `BUILD_PLAN` versions and `AGENT_EXECUTION`s.
- An `AGENT_EXECUTION` records one run of one agent: status, start and end times, duration, attempt number, parallel group, error info. It has many `LLM_CALL`s (provider, model, prompt and completion tokens which can be null, latency, estimated cost), `GENERATED_FILE`s, `LOG_EVENT`s and `TEST_RESULT`s.
- `MODEL_CONFIG` holds provider, model and token prices. Cost per call = tokens × price. Build cost is the sum over its calls, stored in `REQUEST.total_cost`.
- `REQUIREMENT` defines many `TEST_CASE`s. `TEST_RESULT` points to both the `TEST_CASE` it checked and the `AGENT_EXECUTION` that ran it. A failed result can trigger `CORRECTION_ATTEMPT`s.
- `BUILD_PLAN` links to `COMPONENT` through `PLAN_COMPONENT` (`is_custom` is true when no library component fits).

## 7. The Clarification Agent in detail

### 7.1 Purpose
It is the first worker agent and the **only point where FORGE talks to the user before building anything**. Its job is to turn a short, vague, incomplete plain-English request (for example "I need a website for my bakery") into a clear, buildable specification that the Planning Agent can trust. It also produces the tests used later to check the finished site.

### 7.2 Why it matters
Most failures in AI-generated sites start with unclear requirements. Fixing ambiguity first means every later agent works from stable input, so there is less rework and fewer wasted model calls. Our related work supports this: ChatDev's "communicative dehallucination" (ask for missing details instead of guessing) is the direct precedent, and AgentCoder argues tests should come from the requirements, not from the code.

### 7.3 Inputs and outputs
- **Input:** the user's original prompt (stored in `REQUEST.prompt`) plus any answers collected so far in earlier rounds.
- **Output**, one of three results each round:
  1. **A list of guided questions** (mostly multiple-choice, per the project proposal) when information is missing.
  2. **Final structured requirements** when the request is complete enough. This includes:
     - a **clarified requirement**: the clear version of the vague prompt (`REQUIREMENT.clarified_text`), plus the structured fields
     - **test cases** (acceptance criteria): what a correct site must do (`TEST_CASE.description` and `expected_result`)
  3. **An out-of-scope notice** (for example payments or an online store) that explains the limit to the user and does **not** pass the request to the planner.

### 7.4 Behaviour, step by step
1. Receive the prompt and any earlier answers.
2. Compare it to a checklist of what later stages need:
   - website type (brochure, catalog, booking or portfolio)
   - pages and sections
   - content to show
   - whether visitors submit forms or make bookings
   - visual preferences **[FILL IN: confirm this matches the implemented checklist]**
3. Check scope. If the request is out of scope, explain and stop.
4. If items are missing or ambiguous, turn each into a short guided question, show it on the clarification screen, and merge the answers into the requirements.
5. If the request is already complete, **ask nothing** and proceed (avoids unnecessary questions and model calls).
6. Stop asking at the round limit **[FILL IN: maximum rounds]**. Report what is still missing instead of looping forever.
7. When done, write `clarified_text`, the structured requirements and the test cases, and hand the requirements to the Context Retrieval and Planning agents.

### 7.5 Rules and design principles
- Never guess missing information. Ask.
- Keep rounds few and questions well chosen: non-technical users abandon long question lists.
- Prefer multiple-choice questions over free text.
- Never pass an out-of-scope request to the planner.
- Failure is reported honestly: a request that cannot be clarified is never silently treated as complete.
- All model calls go through the LLM gateway. The agent contains no provider-specific code.

### 7.6 What gets stored
| What | Where |
|---|---|
| Original vague prompt | `REQUEST.prompt` |
| Each question and answer, with round number | `CLARIFICATION` (`round_no`, `question`, `answer`) |
| Clear final requirement, versioned for revisions | `REQUIREMENT` (`version`, `clarified_text`, `status`) |
| Generated test cases | `TEST_CASE` (linked to `REQUIREMENT`) |
| The agent's run: status, time, attempts, errors | `AGENT_EXECUTION` (`agent_name` = Clarification) |
| Its model calls: tokens, latency, cost | `LLM_CALL` (via `MODEL_CONFIG` prices) |
| Log messages | `LOG_EVENT` |

Later, `TEST_RESULT` links back to each `TEST_CASE`, so we can report which requirements passed or failed.

### 7.7 Related requirements and tests
- **Requirements:** FR-01 (accept natural-language description), FR-02 (identify missing or ambiguous requirements and ask questions). Generating test cases and a clarified requirement is **new** and is not yet written into the report's requirements or test cases.
- **Use case:** "Generate a Website", alternative flows (incomplete request, unsupported request).
- **Designed test cases (not yet executed):**
  - TC-01: detailed request → structured requirements, no question asked
  - TC-02: vague request ("a website for my shop") → at least one guided question, no final requirements yet
  - TC-03: answers to TC-02's questions → requirements updated, agent proceeds
  - TC-04: online store with card payments → limitation explained, request not passed on
  - TC-05: repeated unhelpful answers → questioning stops at the limit and missing info is reported
- Tests that depend on an LLM are repeated several times, and a failed model call never counts as a pass.
